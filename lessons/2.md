# Power Query: Data Import, Cleaning and Transformation

## From manual cleaning to a repeatable process

Real-world data is rarely delivered in the exact structure required for analysis.

Typical problems include:

- blank rows;
- extra title rows;
- incorrect data types;
- inconsistent text values;
- duplicated records;
- multiple files with the same structure;
- information stored in column names;
- missing reference keys.

A manual workflow may work once, but it is difficult to audit and must be repeated when the next file arrives.

Power Query records transformation logic so that the same process can be executed again.

Power Query can be understood as an ETL tool:

- **Extract** — connect to the source;
- **Transform** — clean, restructure, combine, and validate data;
- **Load** — send the final result to Excel or the Data Model.

```quiz
question: What is the main advantage of recording transformations in Power Query?
A: The same transformation process can be repeated when new data arrives.
B: Excel formulas are no longer needed anywhere.
C: Every source file becomes read-only.
D: Data-quality problems are corrected automatically.
correct: A
explanation: Power Query turns repeated manual preparation into a transparent sequence of steps that can be refreshed on new data.
```

## The Power Query workflow

A typical Power Query process contains four stages:

1. connect to a source;
2. inspect the structure;
3. define transformation steps;
4. load the result.

The Power Query Editor records transformations in **Applied Steps**.

A typical sequence might include:

- Source
- Promoted Headers
- Changed Type
- Removed Columns
- Filtered Rows
- Renamed Columns

The output of one step becomes the input to the next.

Power Query is therefore a transformation pipeline, not a collection of manual edits.

## Data types are analytical meaning

Common Power Query data types include:

- Text;
- Whole Number;
- Decimal Number;
- Date;
- Date/Time;
- Logical.

A value that looks numeric does not necessarily represent a number.

For example:

`00127`

may be a Product ID. If it is converted to Whole Number, meaningful leading zeros disappear.

Dates require similar care.

`03/04/2026`

may be interpreted differently depending on locale.

Do not blindly trust an automatically generated `Changed Type` step. Verify that the assigned type matches the meaning of the field.

```quiz
question: A Product ID column contains values such as 00127 and 00128. Which type is usually safest if leading zeros are meaningful?
A: Text
B: Whole Number
C: Percentage
D: Logical
correct: A
explanation: Identifiers are labels rather than quantities, and Text preserves meaningful leading zeros.
```

## Cleaning text and structural noise

Useful Power Query cleaning operations include:

- Trim;
- Clean;
- Uppercase;
- Lowercase;
- Replace Values;
- Remove Rows;
- Remove Columns;
- Rename Columns;
- Split Column.

Suppose a Region column contains:

- `North`
- ` north `
- `NORTH`
- `North `

These may represent the same business value while remaining different strings.

Before grouping or matching text keys, standardize them deliberately.

Do not apply the same transformation blindly to every field. A product code may be case-sensitive while a region label may not be.

## Split and merge columns

Suppose a column contains:

`P101-North`

Power Query can split it into ProductCode and Region using a delimiter.

Power Query can also split by character count or position.

If splitting or combining fields is part of recurring data preparation, the transformation normally belongs in Power Query rather than in repeated manual worksheet operations.

## Reshaping with Unpivot

Consider:

`Product | January | February | March`

This is convenient for reading, but the month is stored in the column name.

A more stable analytical structure is:

`Product | Month | Revenue`

Power Query creates this structure with **Unpivot**.

Unpivot is especially useful when new periods or categories would otherwise create new columns.

A useful rule is:

> New observations should usually create new rows, not new structural columns.

```quiz
question: Which transformation converts Jan, Feb, and Mar columns into a Month column and a Value column?
A: Merge
B: Append
C: Unpivot
D: Group By
correct: C
explanation: Unpivot moves repeated period or category information from column names into row values.
```

## Append versus Merge

### Append

Append combines similar datasets vertically.

January + February + March transactions become one transaction table.

Use Append when the tables contain the same type of records and compatible columns.

### Merge

Merge enriches one dataset with information from another using a key.

For example, Sales may contain Product ID while Products contains Product Name and Category.

A Merge can attach those descriptive attributes to the Sales table.

### Left Outer Join

A Left Outer Join keeps every row from the first table and adds matching fields from the second.

If `P-999` exists in Sales but not in Products, the transaction remains visible and the joined fields are null.

This is useful for data-quality control.

An Inner Join would remove unmatched rows, which may silently remove revenue from the analysis.

### Validate every merge

After a merge, verify:

- row count before;
- row count after;
- unmatched keys;
- uniqueness of keys in the reference table.

If a reference key occurs twice, one transaction may become two rows after expansion.

The query can succeed technically while the analytical result becomes wrong.

```quiz
question: Which operation should combine January, February, and March transaction files that have the same structure?
A: Append
B: Merge
C: Pivot
D: Replace Values
correct: A
explanation: Append stacks rows from compatible tables into one combined dataset.
```

## Combining files from a folder

Folder ingestion is one of the strongest Power Query workflows.

Suppose monthly files are stored as:

- `sales_2026_01.xlsx`
- `sales_2026_02.xlsx`
- `sales_2026_03.xlsx`

Instead of opening each file manually, connect Power Query to the folder.

Power Query can:

1. read the file list;
2. apply the same transformation logic to each file;
3. combine the results.

When a new file arrives, place it into the folder and refresh.

This works best when the files follow a stable schema:

- same sheet name;
- same column names;
- same data types;
- same basic structure.

Think of the expected schema as a source contract.

## Parameters and query design

Parameters make important query settings explicit.

Examples include:

- folder path;
- reporting date;
- selected region;
- threshold;
- environment.

Do not convert every constant into a parameter. Use parameters when values are expected to change or meaningfully control query behavior.

Larger solutions can separate queries by responsibility:

- `src_Sales` — raw source;
- `src_Products` — raw reference data;
- `stg_Sales` — cleaned transactions;
- `fact_Sales` — final analytical table.

## Refresh and validation

Refresh automates transformation, but it does not prove correctness.

Useful checks include:

- row count;
- total revenue;
- minimum and maximum dates;
- null count;
- unique-key count;
- unmatched keys after Merge.

A query that completes successfully can still return the wrong analytical result.

Automation removes repeated manual actions. It does not remove the need for controls.

```quiz
question: Which check is especially important after merging a transaction table with a reference table?
A: Compare row counts and inspect unmatched keys.
B: Change the worksheet theme.
C: Convert every column to text.
D: Delete all null values automatically.
correct: A
explanation: Row-count changes and unmatched keys can reveal duplicate reference keys, lost records, or other merge defects.
```
